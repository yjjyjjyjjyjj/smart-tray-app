# 아마따 Arduino 연동 개발 인수인계서

기준일: 2026-11-01

대상: Arduino 하드웨어·펌웨어 담당자와 Android 앱 연동 담당자

아마따는 트레이 2칸과 우산 공간 1칸의 상태를 휴대폰에 전달해 외출 시 놓고 가는 물건을 알려주는 장치입니다. Arduino는 센서 측정·출력 제어·LCD 표시를 담당하고, Android는 Bluetooth 연결·날씨 조회·설정 화면·시스템 알림을 담당합니다.

**현재 HC-06 연결 기반은 구현되어 있으나, 실제 센서 디코더와 LED·살균·팬·LCD 제어 명령은 미구현입니다.** 저장소에 실제 Arduino 펌웨어와 확정된 송수신 패킷이 없습니다. 아래의 **현재 앱 내부 자료형**은 코드에 존재하는 형식이고, **협의용 메시지 예시**는 양 팀이 검토할 초안입니다. 예시를 그대로 전송해도 현재 앱이 해석하거나 응답하지 않습니다.

제품 요구사항은 [README](../README.md), 정확한 알림 제목·본문은 [푸시 메시지 리스트](푸시메시지_리스트.md), Android 연결 수명과 권한은 [HC-06 통신 문서](HC06_INTEGRATION_NOTES.md)를 기준으로 합니다. 이 문서는 Arduino 구현에 필요한 데이터와 합의 사항에 집중합니다.

## 1. 담당 범위와 구현 상태

| 영역 | Arduino 담당 | 앱 담당 | 현재 상태 |
| --- | --- | --- | --- |
| 센서 | 로드셀·적외선·문 센서 측정, 보정·노이즈 처리, 상태 전송 | 패킷 검증·상태 반영·기록 | 앱 내부 모델 있음, 실제 디코더 대기 |
| Bluetooth | HC-06 설정, UART 송수신 | Classic 검색·시스템 페어링·RFCOMM 연결·재연결 | 앱 연결 코드 구현, 물리 HC-06 검증 대기 |
| LED·살균·팬 | 타이머와 물리 출력, 실행·완료·오류 통지 | 사용자 설정, 명령 전송, 실제 결과 표시 | 설정 UI·휴대폰 저장 있음, 제어 연동 대기 |
| 날씨 | 전달받은 예보의 LCD 출력·만료 처리 | 위치 권한·기상청 조회·표시 구간 구성·전송 | 앱 날씨 조회 있음, LCD 연동 대기 |
| 알림 | 판단에 필요한 센서 상태 전달 | Kotlin에서 조건·시간 판단 후 Android 시스템 알림 | 정책 구현, 실제 센서 연동 대기 |

알림은 휴대폰에서 생성하는 **로컬 시스템 알림**입니다. Arduino가 알림 문구를 만들거나 FCM·서버에 접속할 필요는 없습니다. 별칭·알림 허용 여부·문 열림 판단 시간도 현재는 앱에서 관리합니다.

## 2. 하드웨어 구성과 공간 식별

| 공간·기능 | 부품 | 전달하거나 제어할 정보 |
| --- | --- | --- |
| 1번 트레이 | 로드셀 1kg급 + HX711 | 물건 유무, 컵 무게를 차감한 물건 무게, 센서 상태 |
| 2번 트레이 | 로드셀 1kg급 + HX711 | 위와 동일, 1번과 독립 |
| 3번 우산 공간 | 적외선 센서 | 우산 유무, 센서 상태. 무게 없음 |
| 현관문 | MC-38 | 열림·닫힘, 읽기 유효성 |
| 각 공간의 LED | 공간마다 RGB LED 1개, 총 3개. WS2812B 계획 | 일반 점등과 보라색 살균 표시가 **동일한 LED를 공유** |
| 우산 건조 | 팬 1개 | 동작 시간, 실제 실행·정지 상태 |
| 날씨 표시 | 기존 1602 LCD 1개 | 16열 × 2행, 왼쪽 2×2칸 도트 아이콘과 오른쪽 영어·숫자. 부품 추가·교체 없음 |
| 통신·제어 | HC-06, Arduino UNO R3 | Classic SPP ↔ UART |

`1`, `2`, `3`은 물리 공간 번호입니다. **현재 앱의 `trays` 배열은 1·2번만 포함**하고 우산은 별도의 `umbrella` 객체입니다. 우산을 `trays[2]`나 3번 로드셀로 보내면 현재 앱의 수신 검증과 맞지 않습니다. 별칭을 바꾸어도 물리 번호는 바뀌지 않습니다.

로드셀의 컵 무게 차감·오프셋·물건 감지 임계값·히스테리시스는 Arduino에서 처리합니다. 앱은 물건 종류를 추론하지 않으며 영점 보정 명령을 사용하지 않습니다. 음수 오차를 0으로 보정할 범위, 범위 초과·센서 미연결 판정, 문·적외선 센서의 HIGH/LOW 의미와 디바운스 시간은 펌웨어에서 정해 공유해야 합니다.

핀 배치, 전원, 모듈 전압과 구동 회로, 팬 최종 모델은 제작 팀이 확정합니다. LCD는 기존 부품을 유지하고 장착된 인터페이스·주소·핀 배치를 확인합니다. 현재 시제품의 살균 표시는 보라색 LED 동작이며 UV 모듈은 없습니다.

## 3. HC-06 연결 조건

| 항목 | 현재 앱 기준 |
| --- | --- |
| 통신 방식 | Bluetooth Classic SPP / RFCOMM. BLE·GATT 사용 안 함 |
| 검색에 표시되는 이름 | 앞뒤 공백 제거 후 **`HC-06` 또는 `AMATTA`**와 대소문자까지 정확히 일치 |
| 장치 식별 | 사용자가 선택한 MAC 주소. 같은 이름도 주소로 구분 |
| 페어링 | Android 시스템 페어링 창. PIN 자동 입력 없음, 최대 60초 대기 |
| 서비스 UUID | `00001101-0000-1000-8000-00805f9b34fb` — 표준 SPP 연결용 |
| 연결 완료 기준 | 실제 `BluetoothSocket.connect()` 성공 |
| 소켓 연결 제한 | 시도당 최대 20초 |
| 연결 유실 후 재시도 | 실패 후 2·4·8·16초, 이후 매번 30초 대기. 횟수 제한 없음. 연결 시도 시간은 별도 |

UART baud rate·데이터 비트·패리티·정지 비트·사용 포트·페어링 PIN을 실제 HC-06 설정으로 알려 주세요. Android RFCOMM에는 Arduino UART 속도를 설정하는 옵션을 보내지 않습니다. UART 설정이나 PIN을 `9600`, `1234` 등으로 가정하지 않습니다.

Kotlin 포그라운드 서비스가 소켓을 소유합니다. 화면 전환·화면 꺼짐·WebView 종료와 독립적으로 수신하도록 구성되어 있습니다. 사용자 연결 해제·서비스 중지는 자동 재연결과 문 확인 대기를 종료합니다. 거리 이탈 중에는 수신할 수 없고, 앱 강제 중지·권한 해제·제조사 절전 제한에서 동작을 보장하지 않습니다. 재부팅 후 자동 시작은 미지원입니다.

## 4. Arduino에서 앱으로 보낼 센서 데이터

### 4.1 현재 앱 내부 자료형

다음 이름은 [FirmwareProtocol.kt](../android/app/src/main/java/kr/ac/gachon/smarttray/bluetooth/FirmwareProtocol.kt)의 **디코딩 결과**입니다. UART 필드 이름이나 직렬화 규격으로 확정된 것은 아닙니다.

| 내부 필드 | 타입·값 | 의미와 제약 |
| --- | --- | --- |
| `DeviceReading.door` | 문자열 `open` / `closed` | 유효한 문 상태. 현재 저장소는 다른 값을 거부 |
| `DeviceReading.trays` | `TrayReading` 목록 | ID 1·2를 중복 없이 정확히 한 번씩 포함 |
| `TrayReading.id` | 정수 1 / 2 | 물리 트레이 번호 |
| `TrayReading.present` | Boolean | 보정·임계값 적용 후 물건 유무 |
| `TrayReading.weight` | 유한한 Double, 0 이상 | 앱 표시 단위 g. 분해능·최대값·오차 처리는 합의 필요 |
| `TrayReading.sensor` | `ok` / `waiting` / `error` | 정상 / 아직 측정 전 / 오류. 오류를 물건 없음으로 취급하지 않음 |
| `TrayReading.ledActive` | Boolean | 일반 LED 동작 표시용. 현재 기본값 false는 실물 확인 결과가 아님 |
| `TrayReading.sterilizationUntil` | Long, 기본값 0 | 앱의 `effectUntil`로 전달하는 종료 시각. 0은 실행 없음, 실행 시 앱 UI가 비교하는 epoch 밀리초 기준 |
| `DeviceReading.umbrella` | `UmbrellaReading?` | 별도 우산 데이터. 생략 시 수신 대기 처리 |
| `UmbrellaReading.present` | Boolean | 우산 유무 |
| `UmbrellaReading.sensor` | `ok` / `waiting` / `error` | 적외선 센서 상태 |

`TrayRepository.accept()`는 연결 중에만 수신값을 반영하고, 문 값·트레이 개수/ID·무게·센서 상태가 잘못되면 전체 수신 결과를 거부합니다. `lastReceived`와 `measuredAt`은 현재 **앱의 수신 시각**으로 기록됩니다. Arduino의 `millis()`를 epoch 시각으로 보내면 안 됩니다.

### 4.2 전송 시점과 신선도

초기 연결·재연결 직후에는 문·트레이 2칸·우산의 **현재 전체 상태**를 얻을 수 있어야 합니다. 이후에는 디바운스된 변화가 생기면 빠르게 전송하고, 변화가 없어도 상태를 주기적으로 전송하는 방식을 권장합니다. 협의 시작값은 **전체 상태 1초 주기 + 변화 시 즉시 전송**이며, UART 처리량과 측정 주기를 확인해 확정합니다.

현재 앱의 센서 신선도는 **45초**입니다. 이는 허용 지연 목표가 아니라 오래된 값의 판정 기준입니다. 문 열림 판단의 최소 시간이 10초이므로 45초에 가까운 주기로 보내면 닫힘을 제때 알 수 없습니다. 센서가 멈췄을 때도 과거 값을 정상 상태로 반복 전송하면 앱이 최신값으로 오인하므로, 측정 경과 시간이나 오류 상태를 함께 구분해야 합니다.

부분 갱신만 전송하려면 앱 디코더가 각 센서의 신선도를 보존하며 전체 상태를 조립하도록 추가 구현해야 합니다. **문 한 필드의 갱신으로 오래된 트레이·우산 값을 최신값으로 재포장하지 않습니다.**

### 4.3 알림에 필요한 상태 변화

정확한 문구는 [푸시 메시지 리스트](푸시메시지_리스트.md)에 있습니다. Arduino는 다음 판단이 가능하도록 상태를 전달합니다.

| 앱 판단 | 필요한 입력 | 동작 |
| --- | --- | --- |
| 소지품 미수거 | 닫힘 → 열림, 정상 트레이의 `present` | 알림이 켜진 1·2번 트레이를 묶어 한 번 안내. 별칭은 앱에서 적용 |
| 현관문 열림 | 닫힘 → 열림 | 같은 이벤트에 미수거 알림이 없을 때 안내 |
| 우산 안내 | 닫힘 → 열림, 정상·최신 우산 있음 | 앱에 유효한 오늘 남은 비 예보가 있을 때만 별도 안내 |
| 문 열림 유지 | 유효한 열림 이후 닫힘 수신 여부 | 사용자 설정 10~300초, 기본 30초. Kotlin 타이머로 판단 |

최초 연결·재연결의 첫 문 상태는 미수거·현관문 열림·우산 알림의 기준값입니다. 첫 패킷이 열림이어도 외출 이벤트로 재생하지 않습니다. 같은 열림의 반복 수신도 새 이벤트가 아닙니다. 다만 **문 열림 유지 감시는 첫 유효한 열림부터 시작할 수 있습니다.**

문이 열린 뒤 N초 안에 유효한 닫힘이 오면 대기를 취소합니다. 연결 유실·EOF·재연결로 기존 기한을 초기화하지 않습니다. 기한에 최신 열림이 확인되면 “현관문이 계속 열려 있어요”, 닫힘을 확인할 수 없으면 “현관문이 닫혔는지 확인해 주세요”라고 안내합니다. 연결 끊김만으로 문 열림이나 외출을 확정하지 않습니다. 예를 들어 30초 설정에서 열림 10초 후 연결이 끊겨도 최초 열림 기준 30초 시점에 확인 알림을 판단합니다.

우산 거치·제거, 물건 거치·제거, LED·살균·팬 시작·종료만으로 시스템 알림을 보내지 않습니다. 예보 조회 중이던 문 열림에서는 예보가 도착한 뒤 우산 조건을 다시 평가할 수 있습니다.

## 5. 앱에서 Arduino로 보낼 설정과 제어

### 5.1 현재 저장하는 설정

아래는 [TrayRepository.kt](../android/app/src/main/java/kr/ac/gachon/smarttray/bluetooth/TrayRepository.kt)의 휴대폰 설정입니다. `savePreferences()` 성공은 **휴대폰 저장 성공**이며 Arduino 적용 성공이 아닙니다.

| 대상 | 현재 앱 설정 경로 | 값·기본값 | Arduino 연동 시 의미 |
| --- | --- | --- | --- |
| 트레이 1·2 일반 LED | `trays[].led.enabled/onDetect/onDoor` | Boolean, 각각 기본 true | 활성화 / 거치 / 문 열림 조건. 아래 제품 요구사항과 정리 필요 |
| 트레이 1·2 살균 | `trays[].effect.enabled/onDetect/onDoor` | Boolean, 각각 기본 false | 활성화 / 거치 시 자동 / 문 열림 시 실행 |
| 트레이 1·2 살균 시간 | `trays[].effect.duration` | **5·10·20·30초**, 기본 10 | 실행 시간. 별도 활성화 스위치 사용 |
| 우산 살균 | `umbrella.effect.enabled/onDetect/onDoor` | Boolean, 각각 기본 false | 활성화 / 우산 거치 시 자동 / 문 열림 시 실행 |
| 우산 살균 시간 | `umbrella.effect.duration` | **5·10·20·30초**, 기본 10 | 팬 시간과 독립 |
| 우산 팬 | `umbrella.fan.duration` | **0·15·30·60초**, 기본 0 | 0은 사용 안 함, 60은 UI의 1분 |

물리 제어에는 공간 ID와 필요한 설정만 전달하면 됩니다. 사용자 별칭·전체 알림·개별 트레이 알림·문 열림 판단 시간·위치 권한·읽음 상태는 현재 앱 판단용으로, 그대로 장치 설정에 복사할 필요가 없습니다. 앱의 `schemaVersion = 2`도 휴대폰 저장 형식 버전이지 통신 프로토콜 버전이 아닙니다.

### 5.2 LED와 살균의 공유 제어

제품 요구사항은 **문이 열릴 때 물건이 남은 공간의 LED를 켜서 위치를 알려주는 것**입니다. 같은 공간의 살균 표시는 동일 부품을 보라색으로 켭니다. 두 기능을 독립된 물리 LED처럼 구현하면 안 됩니다.

현재 웹 UI·가상 동작에는 “물건을 놓으면 켜기”가 남아 있고, 우산 공간의 일반 LED 설정·네이티브 실제 출력 모델도 완성되지 않았습니다. 이 부분은 앱 팀이 README의 공유 LED 요구사항에 맞춰 정리해야 합니다.

펌웨어 제어 규칙은 다음을 확정해야 합니다.

- 일반 점등과 살균이 겹칠 때의 우선순위·색상·밝기, 살균 종료 후 소등 또는 일반 점등 복귀.
- 거치·문 열림 자동 실행을 **Arduino에서 판단할지 앱 명령으로 실행할지**. 두 곳에서 동시에 시작하지 않도록 책임을 하나로 정합니다. 연결 유실 중에도 자동 동작하려면 Arduino 측 판단이 필요합니다.
- 살균 OFF·물건/우산 제거·센서 오류·연결 유실·전원 재시작 시 중지/유지 정책. 현재 가상 동작을 실제 하드웨어 정책으로 자동 확정하지 않습니다.
- 수동 살균은 활성화되어 있고 정상·최신 센서가 물건 있음을 나타낼 때만 허용하며, 이미 동작 중인 요청은 시간을 연장하지 않도록 처리하는 방향으로 맞춥니다. 앱에는 이 제한이 있고, 실제 펌웨어도 중복 명령 방어가 필요합니다.

상태 반환에는 **실제 출력 모드(꺼짐/일반 점등/살균), 실행 여부, 남은 시간, 종료 이유**가 필요합니다. 설정의 `enabled`를 실제 `ON`으로 표시하지 않습니다. 앱이 살균 종료 표시를 위해 쓰는 `effectUntil`은 장치의 남은 시간을 수신 시점에 변환하는 방식으로 연결할 수 있으며, 변환 규칙과 지연 보정은 합의해야 합니다.

### 5.3 우산 팬

우산을 넣으면 설정된 시간 동안 팬이 동작하도록 합니다. 0초는 사용하지 않습니다. 동작 중 우산 제거, 시간을 0초로 변경, 센서 오류, 같은 우산의 반복 감지, 연결 끊김 시 처리와 재시작 조건을 확정해야 합니다.

팬 실행 시간은 Arduino에서 관리하도록 권장합니다. 앱 화면의 JavaScript 타이머에 의존하면 화면이 종료될 때 물리 출력 시간을 보장할 수 없습니다. 팬 실제 동작 여부·남은 시간·완료·오류를 앱으로 돌려주어야 하며, 현재 앱의 시간 설정 저장만으로 팬 실행이 확인되는 것은 아닙니다.

### 5.4 명령 적용 결과와 설정 복원

연동 규격에는 상태 조회, 설정 적용, 필요한 수동 시작·중지, 명령 결과를 포함합니다. UART에 썼다는 사실, 장치가 요청을 접수한 사실, 물리 동작을 시작한 사실, 동작을 완료한 사실을 구분합니다.

설정 저장 위치(휘발성 RAM / 비휘발성 저장소), 재부팅 기본값, 앱·장치 설정이 다를 때의 기준을 합의해야 합니다. 재연결 때 자동으로 수동 시작 명령을 재실행하지 않습니다. 설정 적용 확인과 실제 상태 재조회 후 화면을 동기화합니다.

## 6. 1602 LCD 날씨 표시

### 6.1 확정된 요구사항

**Arduino UNO + HC-06 + 기존 1602 LCD(16열 × 2행)를 사용하며, 디스플레이 부품을 추가하거나 교체하지 않습니다.** 기존의 한글·고정 3시간 구간 표시 설명은 이번 **사용자 정의 도트 아이콘과 영어·숫자 표시** 요구사항으로 대체합니다.

- 왼쪽 **2칸 × 2줄**을 하나의 큰 날씨 아이콘으로 사용합니다. 해·구름·비·눈 아이콘을 준비합니다.
- 오른쪽 **첫 줄은 날씨 이름**, **둘째 줄은 비 예보 시간대 또는 안내 문구**입니다.
- 시간대는 **비 예보에 대해서만** 표시합니다. 눈 오는 시간대는 계산·전송·표시하지 않습니다. 눈 유무 판단은 시간대 계산과 구분합니다.
- 눈만 예보된 경우 `SNOW` / `NO RAIN`으로 표시합니다. **`NO RAIN/SNOW`는 확인 대상 예보 범위에서 비와 눈이 모두 없다고 확인된 경우에만** 사용합니다.
- 미수신·조회 실패·불완전한 예보·만료는 `NO DATA` 등으로 구분하며 `SUNNY`, `NO RAIN`, `NO RAIN/SNOW`로 대체하지 않습니다.

| 표시 상황 | 큰 아이콘 | 오른쪽 첫 줄 | 오른쪽 둘째 줄 |
| --- | --- | --- | --- |
| 비 예보, 예시 구간 14~18시 | 비 | `RAIN` | `14:00-18:00` |
| 눈만 예보되고 비 예보 없음 | 눈 | `SNOW` | `NO RAIN` |
| 맑음, 비·눈 예보 모두 없음 | 해 | `SUNNY` | `NO RAIN/SNOW` |
| 흐림, 비·눈 예보 모두 없음 | 구름 | `CLOUDY` | `NO RAIN/SNOW` |
| 유효한 날씨 정보 없음 | 맑음 등 정상 날씨로 표현하지 않음 | `NO DATA` | 공란 처리안 |

위 네 정상 예시는 **현재 표시 날씨와 이후 예보가 충돌하지 않는 경우**입니다. 현재 맑지만 이후 비나 눈이 예보되어 있으면 위 맑음 행을 그대로 적용하지 않으며, 첫 줄·아이콘과 안내 문구의 우선순위는 6.6절에서 합의합니다. `NO RAIN`은 비가 없다는 뜻이고 눈이 없다는 뜻은 아닙니다.

### 6.2 16칸 배치와 길이 확인

구현 배치안은 각 줄의 **1~2열 아이콘 + 3열 공백 + 4~16열 텍스트**입니다. 텍스트에 13칸을 사용할 수 있습니다. 0부터 세는 LCD 좌표로는 아이콘이 열 0·1/행 0·1, 텍스트 시작이 열 3/행 0·1입니다.

아래 `A`, `B`, `C`, `D`는 실제 영문자가 아니라 아이콘의 좌상·우상·좌하·우하 사용자 정의 문자 한 칸씩을 나타냅니다. 양옆 테두리는 LCD 칸에 포함하지 않습니다.

```text
 1234567890123456
|AB RAIN         |
|CD 14:00-18:00  |
```

| 문구 | 텍스트 칸 수 | 아이콘 2칸 + 간격 1칸 포함 | 16칸까지 남는 칸 |
| --- | ---: | ---: | ---: |
| `RAIN` | 4 | 7 | 9 |
| `SNOW` | 4 | 7 | 9 |
| `SUNNY` | 5 | 8 | 8 |
| `CLOUDY` | 6 | 9 | 7 |
| `14:00-18:00` | 11 | 14 | 2 |
| `NO RAIN` | 7 | 10 | 6 |
| `NO RAIN/SNOW` | 12 | 15 | 1 |
| `NO DATA` | 7 | 10 | 6 |

**모든 표시 문구는 16칸 이내**입니다. 미수신 시 아이콘 영역을 비우더라도 해당 2칸을 예약해 같은 정렬을 유지할 수 있습니다. 글자 수는 ASCII 문자·공백 기준이며, 시간 구분에는 `-`를 사용합니다. 여러 비 시간대를 한 줄에 이어 붙이지 않고 한 구간씩 표시하는 방향으로 협의합니다. 짧은 문구로 바꿀 때는 오른쪽 13칸의 남은 부분을 공백으로 덮어 이전 글자가 남지 않도록 합니다.

### 6.3 큰 아이콘과 사용자 정의 문자

일반적인 HD44780 호환 LCD의 5×8 도트 사용자 정의 문자는 CGRAM에 **최대 8개**를 등록할 수 있습니다. 큰 아이콘 하나를 **좌상·우상·좌하·우하 4개 패턴**으로 나누어 왼쪽 2×2칸에 표시합니다. 한 아이콘의 도트는 논리적으로 10×16개지만 실제 LCD의 문자 칸·행 사이에는 간격이 있으므로 연속된 그래픽 화면처럼 가정하지 않습니다. [HD44780U 데이터시트](https://www.sparkfun.com/datasheets/LCD/HD44780.pdf)

해·구름·비·눈의 패턴 원본은 펌웨어에 보관하고, **현재 표시할 아이콘의 4개 조각만 등록**합니다. 날씨가 바뀌면 같은 슬롯의 패턴을 교체합니다. 네 아이콘의 16개 조각을 CGRAM에 동시에 등록하는 설계는 사용하지 않습니다. 슬롯 번호, 패턴 교체 중 임시 소거·재출력 순서와 깜빡임 억제 방식은 사용하는 라이브러리에 맞춰 정합니다.

### 6.4 현재 앱 구현 상태

### 6.5 추가 개발 항목과 전달 정보

**역할:** 앱이 날씨 조회·해석·표시 우선순위 선택·비 시간대 계산을 맡고, HC-06 Bluetooth Classic SPP로 결과를 전달합니다. Arduino는 수신값의 유효성을 확인해 아이콘과 영어·숫자를 표시합니다. Arduino에서 기상청을 호출하거나 원시 `PTY`·`SKY`를 다시 해석하는 구조가 아닙니다.

| --- | --- | --- |
| 표시할 날씨 종류 | 네 아이콘과 첫 줄 이름 선택 | 앱의 시간별 상태에서 LCD용 상태로 변환 필요 |
| 비 예보 시간대 목록 | 둘째 줄 `HH:mm-HH:mm`, 여러 구간 순환에 사용 | 앱 계산 있음, 전송 형식·순환 방식 미정 |

앱 팀은 표시 상태와 안내를 결정하는 변환 계층, 눈 예보 유무 판정, LCD 전송·재연결 갱신 경로를 추가합니다. Arduino 팀은 네 가지 4분할 도트 패턴, 합의된 메시지 수신, 2×2 아이콘·두 줄 텍스트 출력, 패턴 교체·잔상 제거·만료·순환 표시를 구현합니다. API 키·원본 좌표·기상청 응답 전체를 Arduino에 보낼 필요는 없습니다.

### 6.6 미정 사항

- **현재 날씨와 이후 비 예보의 우선순위:** 현재 맑고 나중에 비가 오면 아이콘/첫 줄을 현재 날씨로 둘지 비 예보로 바꿀지, 둘째 줄을 어떻게 조합할지. 현재 눈과 이후 비, 현재 맑음과 이후 눈도 포함해 정합니다. 비와 눈이 섞인 `rain-snow`, 소나기, 구름 많음을 네 아이콘과 이름에 매핑하는 세부 규칙도 합의합니다.
- **예보 확인 범위:** 현재 코드는 오늘 남은 시간을 사용합니다. 내일 등 이후 날짜까지 확장할지와 `NO RAIN`/`NO RAIN/SNOW`가 보장하는 범위를 정합니다. 날짜가 다른 비 구간을 날짜 표시 없이 같은 시간으로 오해하지 않게 해야 합니다.
- **여러 비 시간대:** 한 번에 한 구간을 표시하는 순서·교체 간격·이미 지난 구간 제거·최대 구간 수. 눈 시간대를 추가하지 않습니다.
- **갱신과 연결 유실:** 날씨 전송·갱신 주기, 재연결 시 재전송, 연결이 끊긴 동안 기존 정보를 유지할 시간. 설정한 유지 시간과 예보 유효기간 중 먼저 도달하는 기한 이후에는 강수 없음 대신 `NO DATA`로 구분합니다. 현재 앱의 1시간 유효기간을 LCD의 연결 유실 허용시간으로 자동 확정하지 않습니다.
- **기존 LCD 인터페이스:** 병렬 연결인지 기존 I²C 모듈인지, 라이브러리·버전·실제 주소·핀 배치. 장착된 부품을 확인하며 부품 추가·교체를 전제로 하지 않습니다.
- **아이콘 가독성:** 5×8 패턴 4개를 조합한 해·구름·비·눈의 구분, 문자 칸·행 사이 간격, 명암·관찰 거리, 패턴 전환 시 깜빡임. 문서의 글자 수 확인과 별도로 실제 LCD에서 검증합니다.

## 7. 데이터 양식 협의안

### 7.1 직렬화와 메시지 경계

아래 JSON은 **필요한 데이터를 함께 검토하기 위한 논리 메시지 예시**입니다. 현재 펌웨어 규격·실제 UART 전송 형식·구분자가 아니며, 아직 코드에 적용하지 않았습니다. 최종 형식은 실제 UNO 메모리·직렬 처리량을 확인한 뒤 JSON 또는 짧은 텍스트/바이너리 중 결정합니다.

양 팀은 구현 전에 다음 항목을 한 번에 확정해야 합니다.

| 항목 | 결정해야 할 내용 |
| --- | --- |
| 프레이밍 | 길이 기반 또는 명시적 구분자 기반, 텍스트라면 개행 종류와 이스케이프 규칙 |
| 인코딩·숫자 | 문자 인코딩 또는 바이트 순서, Boolean 표현, g의 정밀도 또는 고정소수점, 초/ms 구분 |
| 크기 제한 | 한 프레임 최대 바이트 수, 수신 버퍼·미완성 프레임 제한 시간, 초과 시 복구 |
| 유효성 | 체크섬/CRC 사용 여부와 계산 범위, 필수 필드·버전·범위 검증 |
| 순서 | 장치 부팅 식별값, 시퀀스 번호, 중복·역순·재부팅·번호 순환 처리 |
| 요청 결과 | 요청 ID, 응답 제한 시간, 재시도 횟수, 같은 요청의 중복 실행 방지, 오류 종류 |
| 초기화 | 연결 직후 상태 조회와 버전/기능 확인 순서, 설정 동기화 시점 |

RFCOMM은 바이트 스트림입니다. 한 번의 `read()`가 메시지 절반이거나 여러 메시지일 수 있습니다. 앱·Arduino 양쪽 모두 부분 프레임을 보관하고 완성된 프레임만 처리해야 합니다. 부팅 로그·디버그 문자열을 센서 데이터와 같은 채널에 섞는 경우에도 명확한 구분 규칙이 필요합니다.

현재 앱의 읽기 버퍼 2,048바이트, 쓰기 요청 64KiB·대기 16건 제한은 **앱 내부 보호 장치**입니다. Arduino의 허용 패킷 크기로 사용하지 않습니다. 출력 실행 중에도 문 닫힘 수신·상태 전송을 처리할 수 있도록 긴 `delay()` 대신 경과 시간 기반 상태 처리를 권장합니다.

### 7.2 전체 상태 예시

**협의용 초안.** `boot_id`·`seq`·측정 경과 시간·문 센서 품질·출력 상태는 현재 앱 모델에 없는 제안 필드입니다. 실물에 맞춘 생성 방식·정수 범위·누락 처리를 함께 정합니다.

```json
{
  "type": "state",
  "version": 1,
  "boot_id": "boot-17",
  "seq": 42,
  "uptime_ms": 15000,
  "door": { "state": "open", "sensor": "ok", "age_ms": 0 },
  "trays": [
    { "id": 1, "present": true, "weight_g": 128.5, "sensor": "ok", "age_ms": 20 },
    { "id": 2, "present": false, "weight_g": 0.0, "sensor": "ok", "age_ms": 20 }
  ],
  "umbrella": { "present": true, "sensor": "ok", "age_ms": 10 },
  "outputs": [
    { "space_id": 1, "led_mode": "normal", "sterilization_remaining_ms": 0 },
    { "space_id": 2, "led_mode": "off", "sterilization_remaining_ms": 0 },
    { "space_id": 3, "led_mode": "sterilization", "sterilization_remaining_ms": 8000 }
  ],
  "fan": { "active": true, "remaining_ms": 15000 }
}
```

- `age_ms`는 프레임 구성 시점에서 마지막 정상 측정까지의 경과 시간입니다. 통신 지연·프레임 자체의 오래됨을 모두 해결하는 값은 아니므로 부팅/순서 정보와 함께 검증합니다.
- `led_mode`는 실제로 선택된 출력 모드입니다. 일반 점등과 살균이 겹칠 때의 우선순위는 5절에서 합의합니다.
- 상태에 오류가 있으면 해당 센서·출력을 오류/알 수 없음으로 구분합니다. `false`, `0`, `off`로만 대체해서 정상적인 비어 있음이나 정지로 보이게 하지 않습니다. 오류 시 숫자 필드를 생략/null로 둘지 최종 스키마에서 정해야 합니다.
- 이 예시의 `version: 1`은 협의안 버전입니다. 앱 설정의 `schemaVersion: 2`와 무관합니다.
- 위 상태 JSON은 공백·개행을 제거하면 UTF-8 기준 581바이트이며 프레임 헤더·구분자·체크섬은 포함하지 않습니다. 최종 버퍼 크기를 정하기 위한 참고치일 뿐이며, 펌웨어 파서의 추가 메모리와 전송 주기를 함께 확인해야 합니다.

### 7.3 설정 적용과 실행 결과 예시

**협의용 초안.** 아래는 3번 공간 설정과 별도의 수동 시작 요청입니다. 자동 시작 책임과 지원 명령은 펌웨어 합의 후 확정합니다.

```json
{
  "type": "set_config",
  "request_id": "app-31",
  "space_id": 3,
  "sterilization": { "enabled": true, "on_detect": true, "on_door": false, "duration_s": 10 },
  "fan": { "duration_s": 30 }
}
```

```json
{
  "type": "command",
  "request_id": "app-32",
  "space_id": 3,
  "action": "start_sterilization"
}
```

```json
{
  "type": "result",
  "request_id": "app-32",
  "status": "accepted"
}
```

```json
{
  "type": "result",
  "request_id": "app-32",
  "status": "completed",
  "reason": "duration_elapsed"
}
```

요청 ID는 재시도 시 유지하고 새 동작에는 새 ID를 부여하는 방식으로 중복 실행을 막습니다. `accepted`는 접수일 뿐 완료가 아니며, 실제 동작 상태는 상태 메시지로 확인합니다. 거절/실패에는 지원하지 않는 명령, 잘못된 시간, 살균 OFF, 물건 없음, 센서 오류, 동작 중 등을 구분할 이유가 필요합니다. 구체적인 결과 값·오류 코드·응답 시간·장치 재부팅 후 요청 처리 정책은 합의 대상입니다.

`set_config`에는 적용된 값과 RAM/비휘발성 저장 여부를 확인할 응답이 필요합니다. 수동 명령의 결과를 잃어버렸을 때는 상태 조회로 복구하고, 무조건 새 시작 명령을 보내지 않습니다. 물리 센서로 출력 피드백을 읽지 않는 회로라면 상태 확인이 출력 명령 적용 확인인지 실제 구동 확인인지도 구분합니다.

### 7.4 LCD 날씨 데이터 제안

**미확정 협의안이며 현재 앱·Arduino에서 지원하는 JSON 명령이 아닙니다.** 6절의 역할과 표시 요구사항을 설명하기 위한 논리 예시입니다. 필드 이름·타입·인코딩·프레임 경계·최대 구간 수·응답 방식은 실제 펌웨어 규격으로 합의해야 합니다. 예시는 현재도 비가 오고 같은 비 구간이 이어져 표시 우선순위가 충돌하지 않는 상황입니다.

```json
{
  "type": "weather",
  "request_id": "app-33",
  "status": "valid",
  "timezone": "Asia/Seoul",
  "now": "2026-11-01T14:00:00+09:00",
  "outlook_start": "2026-11-01T14:00:00+09:00",
  "outlook_end": "2026-11-02T00:00:00+09:00",
  "display_condition": "rain",
  "has_rain_forecast": true,
  "has_snow_forecast": false,
  "rain_windows": [
    { "start": "2026-11-01T14:00:00+09:00", "end": "2026-11-01T18:00:00+09:00" }
  ],
  "fetched_at": "2026-11-01T13:55:00+09:00",
  "expires_at": "2026-11-01T14:55:00+09:00"
}
```

이 예시를 수신하면 왼쪽에는 큰 비 아이콘, 오른쪽에는 `RAIN` / `14:00-18:00`을 표시합니다.

- `display_condition`는 앱이 합의된 우선순위로 선택한 LCD 표시 상태입니다. 원시 날씨를 Arduino가 재해석하도록 하지 않습니다.
- `rain_windows`는 비 시간대만 포함합니다. `has_snow_forecast`는 눈 예보 **유무**이며 눈 시간대 필드를 추가하지 않습니다. 두 Boolean은 같은 `outlook_start`~`outlook_end` 범위의 유효한 자료로 판정합니다.
- 유효한 눈 단독 예보라면 표시 상태 `snow`, 비 없음·눈 있음, 비 구간 빈 목록으로 `SNOW` / `NO RAIN`을 표현할 수 있습니다. 비·눈 모두 없음이 확인된 맑음/흐림에만 `NO RAIN/SNOW`를 사용합니다.
- 불완전·미수신·만료 상태를 두 Boolean의 false나 빈 구간 목록으로만 표현하지 않습니다. 별도 유효 상태를 먼저 확인하고 `NO DATA`를 표시하도록 합의합니다. 눈 유무가 불명확해도 `NO RAIN/SNOW`로 내보내지 않습니다.
- ISO 날짜 문자열은 의미 전달용입니다. 실제 전송은 장치 자원에 맞게 확정하며, KST의 다음 날 `00:00`을 LCD에 `24:00`으로 보여줄지 등 날짜 경계 표기를 함께 정합니다.

## 8. 연결 후 처리 순서와 앱의 추가 작업

### 8.1 합의 후 구현할 순서

1. 앱이 사용자가 선택한 HC-06과 페어링·소켓 연결을 완료합니다.
2. 버전·지원 기능·부팅 식별값과 전체 현재 상태를 확인합니다. 장치 자발 전송/앱 조회 중 방식은 합의합니다.
3. 앱은 첫 센서값을 기준 상태로 반영합니다. 과거 외출 이벤트나 완료된 수동 동작을 재생하지 않습니다.
4. 필요한 LED·살균·팬 설정을 동기화하고 장치 적용 결과를 확인합니다.
5. 주기 상태·변화 상태를 계속 수신합니다. Kotlin이 알림을 판단하고 UI가 실제 상태를 표시합니다.
6. 유효한 날씨를 확보하면 LCD용 표시 날씨·비 시간대·비/눈 유무·유효성 정보를 전송합니다. 전송·갱신·재연결 규칙은 6.6절의 합의 사항을 적용합니다.

2~6번의 실제 패킷 경로는 아직 구현 전입니다. 재연결 시에도 같은 흐름을 사용하며, 앱에서 이미 시작한 문 닫힘 확인 기한은 유지합니다.

### 8.2 현재 코드에서 반드시 확장할 지점

| 항목 | 현재 코드의 제약 | 앱 팀 후속 작업 |
| --- | --- | --- |
| 센서 해석 | `PendingFirmwareProtocol.feed()`가 항상 빈 목록 반환 | 합의된 프레임 버퍼·디코더 구현, 범위·순서·측정 경과 검증 |
| 문 센서 오류 | `door`는 open/closed만 수용, 별도 문 품질 없음 | 오류·미측정 문을 정상 열림/닫힘으로 변환하지 않도록 모델·정책 확장. 현 구조 유지 시 해당 전체 입력은 반영 불가 |
| 부분 상태·오래된 측정 | 수신 시각으로 센서 신선도 기록 | 각 센서 측정 시각/품질 보존, 오래된 캐시의 최신화 방지 |
| 우산 실제 출력 | `UmbrellaReading`에 팬·살균·일반 LED 상태 없음 | 우산 출력 필드와 저장소·UI 매핑 추가 |
| 공유 LED | 일반 점등 Boolean과 살균 종료 시각 중심 | 공간별 출력 모드와 충돌 규칙 반영, 기존 onDetect 옵션 정리 |
| 명령 결과 | `feed()` 반환형은 `List<DeviceReading>`만 지원 | 센서 외 설정 응답·명령 결과·기능 정보의 디코딩/분배 경로 추가 |
| 명령 전송 | `SmartTrayPlugin.command()`는 `PROTOCOL_NOT_CONFIGURED` 오류 | 검증·인코딩 → 서비스 → `RfcommSession.write()` 연결, 요청 결과 추적 |
| 장치 설정 동기화 | `savePreferences()`는 휴대폰 저장만 수행 | 적용 대기·장치 확인·실패·재연결 재조정 구분 |
| LCD 날씨 | 시간별 상태와 비 구간 계산은 있으나 LCD 변환·전송 없음 | 표시 우선순위·눈 유무 판정·날짜 경계·만료·전송 구현. 눈 시간대는 추가하지 않음 |

소켓 쓰기 완료만으로 설정 적용이나 살균·팬 동작 성공을 표시하지 않습니다. 현재 native 살균 실행은 미지원으로 막혀 있고, 브라우저 시뮬레이션 성공은 Arduino 명령 지원 근거가 아닙니다.

## 9. 공동 검증 시나리오

아래는 **앞으로 수행할 실물 연동 검증**입니다. 기존 앱 자동 테스트 통과와 구분해 결과를 남깁니다.

| 시험 | 기대 결과 |
| --- | --- |
| 이름·페어링·PIN | 지정 이름만 검색, 같은 이름은 주소 구분, 취소/오입력/타임아웃에서 미연결 |
| 연결 직후 상태 | 두 트레이와 우산의 실제 상태 일치. 연결됨과 센서 수신 완료 구분 |
| 분할·병합 수신 | 한 메시지를 여러 조각으로, 여러 메시지를 한 번에 보내도 순서대로 한 번씩 해석 |
| 비정상 프레임 | 너무 긴/깨진/누락/잘못된 버전·ID·무게·센서 상태 입력을 거부하고 다음 정상 프레임에서 복구 |
| 측정 정지·재부팅 | 과거 값 재전송을 최신으로 오인하지 않음. 부팅 식별값·순서 초기화 처리 |
| 첫 패킷 열림 | 미수거·우산 외출 알림 없음, 문 열림 유지 대기는 시작 가능 |
| 닫힘 → 열림 | 남은 1·2번 트레이를 한 알림으로 묶음. 대상이 없으면 설정에 따라 문 열림 알림 |
| 우산과 날씨 | 우산 있음 + 오늘 남은 유효 비 예보일 때만 안내. 우산 넣기/빼기만으로 무알림 |
| 문 열림 기한 | 10초·30초·300초에서 확인. 반복 열림 수신·시간 수정이 열린 시각을 초기화하지 않음 |
| 문 열린 채 거리 이탈 | 원래 기한에 닫힘 확인 불가 알림 1회. 기한 전 재연결·유효 닫힘이면 취소 |
| 사용자 연결 해제 | 재연결·기존 문 확인 대기 종료. 늦은 콜백으로 다시 연결하지 않음 |
| 화면 꺼짐·다른 앱·최근 앱 제거 | 서비스 실행이 허용되는 동안 센서 수신·알림 유지. 강제 중지와 구분 |
| 살균·공유 LED | 1·2·3번 공간에서 5/10/20/30초와 OFF 확인, 중복 시작·일반 점등과의 충돌·종료 후 모드 확인 |
| 우산 팬 | 0초 비활성, 15/30/60초 실행, 거치·제거·센서 오류·설정 변경 정책 확인 |
| 명령 응답 유실 | 성공으로 단정하지 않음. 상태 조회/같은 요청 ID 처리로 중복 실행 방지 |
| 재부팅·설정 복원 | 합의된 기본값/저장값 일치, 재연결 시 수동 실행 명령을 재생하지 않음 |
| LCD 예보 | 6.1절 네 표시 예시 일치, 비 시간대만 표시, 눈 단독은 SNOW / NO RAIN, 비·눈 모두 없을 때만 NO RAIN/SNOW, 미수신·누락·만료는 NO DATA |
| LCD 레이아웃·아이콘 | 두 줄 모두 16칸 이내, 왼쪽 2×2칸·오른쪽 13칸, 4패턴 교체로 해·구름·비·눈 표시, 칸 사이 간격·깜빡임·잔상 확인 |
| LCD 갱신·연결 유실 | 합의된 우선순위·여러 비 구간 순환·재연결 갱신·정보 유지 기한·날짜 경계 확인. 오래된 값을 강수 없음으로 표시하지 않음 |

검증 시 펌웨어 버전, Android APK/커밋, 하드웨어 배선 버전, 설정값, 양방향 원본 바이트, 실제 출력 결과를 함께 기록합니다. [검증 기록](VALIDATION.md)에 자동 테스트·가상 데이터·물리 장치 결과를 나누어 남깁니다.

- [ ] 센서 논리값·무게 단위/정밀도/범위, 컵 차감·임계값·디바운스·오류 판정, 측정/전송 주기.
